## 一、 现有系统真实代码与数据库现状对照

很多人以为改造多 Agent 需要重写大半个系统，但**实际上你的 Supabase 数据库和前端页面已经完成了 75% 的基础架构**：

### 1. 现有的数据库表结构（真实 Supabase）
* **`skill_platform.skills`**：技能表，已完全支持动态录入 Prompt 模板、输入 Schema、测试用例、代码。
* **`skill_platform.agent_profiles`**：Agent 配置表，**当前已经存在以下字段**：
  * `id`：主键（目前写死为 `'default'`）；
  * `name`：Agent 名称（如：'服务助理'）；
  * `role_desc`：人设提示词；
  * `reply_style`：回复风格；
  * `service_flow`：服务流程指引；
  * `taboos`：禁忌话术列表（JSON 数组）；
  * `skill_mode`：`'auto'`（自动路由）/ `'manual'`（人工指定）；
  * `skill_ids`：该 Agent 允许调用的技能 ID 列表（JSON 数组）。
* **`skill_platform.tickets` / `ticket_inputs`**：工单与表单输入表，已实现根据技能动态字段自动存储。

### 2. 现有的前端页面（真实 Web UI）
* **`web/src/pages/AgentProfile.tsx`（服务配置页）**：已经实现可视化编辑 Agent 名称、人设描述、回复风格、服务流程、禁忌词、勾选启用的技能列表，并一键保存到数据库。
* **`web/src/pages/AgentLogs.tsx`（全链路日志页）**：已实现按人维度聚合对话流、卡片折叠展开、事件流式追踪。

## 二、 核心解耦方案：从单一全局配置到多 Agent 实例

### 1. 明确目标：解耦不是做复杂的自动路由器
我们**不需要**做一个由超级大脑动态把任务分给 10 个子 Agent 的复杂路由网络，而是做**「多 Agent 实例独立配置与管理」**：
* 实例 1：`health_assistant`（医疗健康解读助手，挂载病历 Wiki 和医学报告技能）；
* 实例 2：`private_sales_advisor`（企微私域转化顾问，挂载产品百科、CRM画像和方案对比技能）；
* 实例 3：`product_support`（产品咨询与售后客服，挂载技术说明书和故障申报技能）。

### 2. 怎么解耦？（数据库与接口只需做 1 处扩展）
* **数据库层面**：现有的 `agent_profiles` 表本来就支持多条记录！目前只是默认读写 `id = 'default'`。
* **前端页面**：在现有的 `AgentProfile.tsx` 页面顶部加一个 **「选择/新增 Agent」** 下拉列表，切换时加载对应的 Agent 配置。
* **调用接口**：在调用 `/api/v1/agent/chat` 时，请求体带上 `agent_id: "private_sales_advisor"`（不传则默认 fallback 到 default），后端直接读取对应的一整套配置。

## 四、 深度剖析：Agent 是如何识别和调用知识库 Function Call 的？

这是整个系统最核心、最精妙的交互环节。这里直接对照**现有代码的真实调用链**与**配置化改造后的防错机制**：

### 4.1 现有的三层运行机制（代码写死在哪里？）

当前系统由 **三个代码位置** 共同完成工具的注册、引导与执行：

```
┌────────────────────────────────────────────────────────────────────────────┐
│ 1. 工具声明层 (Tools Schema)                                               │
│ 位置: server/src/agentService.ts (第 301~320 行 WIKI_TOOLS 数组)            │
│ 作用: 向大模型 API (Gemini/豆包) 声明工具名称、功能描述 (description) 与参数  │
├────────────────────────────────────────────────────────────────────────────┤
│ 2. 显式引导层 (Prompt Tool Hint)                                           │
│ 位置: llmwiki/server.cjs (第 332~338 行 buildHealthContext)                │
│ 作用: 在注入的 index.md 末尾附加文字提示，明确告诉模型：                    │
│      "📋 可按需调用以下工具获取更多档案：                                    │
│       - 历史病史/化验/生理信号 → 工具 get_medical_history                   │
│       - 当前用药方案/护理要程/监测目标 → 工具 get_medication_plan"          │
├────────────────────────────────────────────────────────────────────────────┤
│ 3. 执行分发层 (Execution Dispatcher)                                       │
│ 位置: server/src/agentService.ts (第 656~662 行)                           │
│ 作用: 收到模型的 tool_call 请求后，根据函数名读取对应 Markdown 页面：        │
│      • if (fnName === 'get_medical_history') → fetchWikiPage('medical_history.md') │
│      • if (fnName === 'get_medication_plan') → fetchWikiPage('medication_plan.md') │
└────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 为什么模型目前「绝不会用错」？
模型能够精准调用的核心原因在于**「双重保险机制」**：
1. **API 参数声明（显式告知有哪些工具）**：`WIKI_TOOLS` 里的 `description` 清晰指明了「当用户询问具体化验指标时调用」。
2. **Prompt 上下文映射（强约束）**：在传入的 Context 文本里，再次明确写明了 `[查询什么意图] → 对应调用 [哪个工具名]`。

---

### 4.3 改成配置化后，如何防错与避免模型混淆？

当系统扩展到多 Agent 场景时（例如私域顾问、产品客服），为了防止不同业务的工具混淆、模型产生幻觉，我们设计了一套**「知识工具四元组模型（Knowledge Tool Spec）」**：

每一个知识工具包含 4 个清晰属性：

| 属性名称 | 说明与作用 | 私域转化 Agent 示例 | 产品技术客服 Agent 示例 |
| :--- | :--- | :--- | :--- |
| **`tool_name`** | 工具唯一英文标识（供 API 识别） | `get_product_matrix` | `get_troubleshooting_doc` |
| **`display_name`** | 中文友好名称（界面展示） | 产品矩阵与选型手册 | 故障自检与排障手册 |
| **`when_to_call`** | **触发时机与调用意图说明（核心防错）** | *当用户询问版本区别、功能对比、价格区间时调用* | *当用户反馈设备报错、功能异常、无法启动时调用* |
| **`target_page`** | 底层关联的文件或资源 | `product_matrix.md` | `troubleshooting.md` |

#### 配置化后系统自动生成的「双重保险」：
1. **自动生成标准 API Schema**：系统根据配置的 `tool_name` 和 `when_to_call` 自动生成传递给 Gemini/豆包的 `tools` 参数；
2. **自动生成 Prompt 强约束引导**：在组装 Context 时，系统自动在提示词中追加强引导块：
   ```text
   ---
   📋 【可用知识库工具清单】请根据用户具体意图按需调用，无需重复读取已有内容：
   - 当询问 [when_to_call] 时 → 必须调用工具 `${tool_name}`
   ```
3. **动态分发执行**：大模型触发调用时，后端直接根据 `target_page` 读取对应文档，无需在代码中写任何 `if-else`。

## 九、 架构深度自检与四大落地避坑指南

为了确保在实际多 Agent 并行运行时系统稳定、不出现交叉污染，在工程实现时需注意以下 4 个关键细节：

### 1. 客户记忆命名空间隔离（Memory Namespace）
* **潜在风险**：如果同一个企微用户既在医疗群咨询体检，又在私域群咨询产品，直接读写同一份 Wiki 会导致客户画像被交叉污染（如销售顾问看到了化验单，医生助手看到了购买预算）。
* **规避方案**：在知识库存储层引入 `agent_id` 命名空间。例如 Wiki 存储路径结构化为 `data/wiki/{clientId}/{agentId}/`，或者在共享的客户 Profile 中以一级标题隔离不同的业务上下文。

### 2. 技能确认守卫生命周期隔离（Guard Lifecycle）
* **潜在风险**：系统目前通过 `skill_confirm_guards` 表维持「用户是否同意使用某技能」的 10 轮防刷守卫（查询条件为 `WHERE session_id = ?`）。若未区分 Agent，用户在 Agent A 中未确认的守卫可能会意外拦截 Agent B 的普通对话。
* **规避方案**：在 `skill_confirm_guards` 写入与查询时，强制带上 `agent_id` 联合过滤（`WHERE session_id = ? AND agent_id = ?`），确保不同业务 Agent 的守卫互不干扰。

### 3. 工单完成异步回发人设一致性（Callback Persona）
* **潜在风险**：用户在 H5 提交表单后，沙箱执行完毕会向企微异步回发报告通知。如果回发模板写死，会导致私域销售 Agent 回复了冰冷的医疗风格通知。
* **规避方案**：在 `tickets` 表中记录创建该工单的 `agent_id`，工单完成后回调时，调用对应 Agent 的通知模板与人设风格组装最终回复。

### 4. 上下文 Token 预算与延迟熔断（Token Budgeting）
* **潜在风险**：当单个请求同时加载了「30 轮历史对话 + 基础 Index/Profile + 近期 24h 上传附件摘要 + 多个 Function Tools 声明」时，Prompt 长度可能激增，导致 LLM 首字延迟变长。
* **规避方案**：
  * 对话历史保持 20~30 轮硬上限；
  * 每个 Function Tool 的 `description` 控制在 60 字以内精炼表述；
  * 将总 Prompt Token 控制在 4,000 ~ 6,000 以内，确保企微端响应速度稳定在 1.5 秒以内。
