# 🏢 Skill-Platform 集中督导型多 Agent 协同架构方案

> **核心设计哲学**：
> 拒绝“多 Agent 社交开会”等虚耗 Token 的拟人化表演，
> 采用 **“严选专业员工 + 统一数据底座 + 集中管理督导（Hub-and-Spoke）”** 的工业级高可靠架构。

---

## 📌 一、 方案背景与设计初心

### 1. 传统多 Agent 协同的陷阱
许多开源多 Agent 系统（如通过私信、群聊、圆桌会议让多个 Agent 自由讨论）在实际业务落地中普遍面临三大死穴：
1. **上下文爆炸与注意力涣散**：所有 Agent 的碎碎念、中间调试日志互相传递，导致 Token 成本指数级上升，模型极易“迷失在海量信息中（Lost in the Middle）”。
2. **职责边界不清与死锁**：Agent A 等 Agent B，Agent B 等 Agent C，缺乏确定性的裁决者，极易陷入死循环或状态打架。
3. **不可控与难以质检**：完全由大模型自由发挥，一旦某个中间环节产生幻觉，错误会迅速向下游滚雪球放大。

### 2. 本方案的核心理念：星型集中管控（Hub-and-Spoke）
* **一线员工（Worker Agents）**：通过平台的 `agents_factory` 严格招聘考核，**只专注自身细分领域**，凭借独立且最小化的上下文高效执行任务，不参与复杂的跨 Agent 社交。
* **管理督导（Supervisor Agent）**：设立唯一的“内部管理 Agent”，拥有全量数据库查询与审计权限，定期或按需对所有一线员工的工作进行**对账、质检、归因诊断与异常干预**。

```
                       ┌──────────────────────────────┐
                       │    👑 内部管理督导 Agent      │
                       │ (全局查数 / 质检对账 / 归因)  │
                       └──────────────┬───────────────┘
                                      │
              ┌───────────────────────┼───────────────────────┐
              │ 审计巡检 / 异常穿透   │ 绩效评估 / 驳回返工   │ 数据汇总 / 诊断报告
              ▼                       ▼                       ▼
      ┌───────────────┐       ┌───────────────┐       ┌───────────────┐
      │ 🩺 顾问员工 A  │       │ 📋 工单处理 B  │       │ 🛍️ 运营员工 C  │
      │ (最小上下文)  │       │ (最小上下文)  │       │ (最小上下文)  │
      └───────┬───────┘       └───────┬───────┘       └───────┬───────┘
              │                       │                       │
              └───────────────────────┼───────────────────────┘
                                      ▼
                        ┌───────────────────────────┐
                        │ 🗄️ 平台统一数据底座 (Postgres)│
                        │ (工单/审计日志/结构化账单) │
                        └───────────────────────────┘
```

## 🏛️ 二、 双层协同架构设计

整个系统清晰地划分为两层：

### 1. 一线员工层（执行层）
* **来源**：由 `agents_factory` 通过严格的自然语言需求解析（`specGenerator`）与 Ralph 试用期考评飞轮（`ralphLoop`），在独立沙箱中通过 95 分大关并经过人工批准上岗。
* **职责**：只负责特定的业务任务（例如：客户答疑、工单流转、调用指定 Skill 处理数据）。
* **原则**：
  * **上下文极简**：只保留当前用户会话及本任务所需的数据，不拉取其他 Agent 的杂乱历史。
  * **结构化交付**：任务完成时，必须通过中间件自动提交一份标准化的 **“交付物账单（Delivery Receipt）”**，记录执行结果、耗时、调用技能与置信度。

### 2. 内部管理督导层（管控层）
* **定位**：对内的“AI 质检主管 & 运营分析师”，充当整个系统的中枢神经与风控守门人。
* **核心职责**：
  1. **定时巡检与对账**：定时扫描过去一段时间内所有员工的任务记录，评估质量与合规性。
  2. **异常穿透与阻断**：发现低分、高耗时、触犯禁忌风险或客户负评时，自动调阅底层日志，判定是否需要人工介入或驳回返工。
  3. **日报与周报自动生成**：为平台管理员生成团队整体绩效、高频问题、技能缺陷分析。
  4. **反哺招聘飞轮**：将经常出错的典型 Case 自动转化为新的考评用例，送回 `agents_factory` 驱动员工提示词的重新进化。

## 🛡️ 三、 内部管理 Agent 的打造与画像定义

与一线业务员工不同，内部管理 Agent（Supervisor Agent）是一个**无外部接口、高分析权限、强逻辑推理**的特殊系统级 Agent。

### 1. 管理 Agent 的画像规范（MetaAgentSpec 结构）
管理 Agent 的定义同样通过 `agents_factory` 规范化生成，但其核心属性具有特殊性：

| 属性字段 | 管理 Agent 的设定 | 设计目的 |
|---|---|---|
| **角色定位 (Role)** | 内部运营质检主管 & 效能分析官 | 仅对内负责，不参与任何 C 端/业务端对话。 |
| **基础模型 (LLM)** | 强逻辑长上下文模型（如 Claude 3.7 / Gemini 3.7 Flash） | 具备极强的规则断言能力、代码阅读能力和抗疲劳长文档分析能力。 |
| **工作流 (Service Flow)** | `拉取指标 -> 规则粗筛 -> 异常穿透 -> 归因判定 -> 输出报告/触发反哺` | 标准化闭环流程，禁止发散式推理。 |
| **核心禁忌 (Taboos)** | 1. 禁止擅自修改业务库数据；<br>2. 禁止向终端用户暴露内部审计信息；<br>3. 遇到不可确定的重大违规必须上报人工，严禁自行静默跳过。 | 确保管理 Agent 自身不会变成不可控的风险源。 |
| **输出风格 (Reply Style)** | 结构化 Markdown 报告、强类型 JSON 质检清单、量化数据表格 | 严禁模糊口语，必须给出明确的扣分原因与归因索引。 |

## 🔒 四、 数据权限体系与安全隔离边界

为了防止管理 Agent 拥有过多权限导致系统风险，必须建立严格的 **“只读穿透 + 最小可信写入 + 网络硬隔离”** 权限体系：

### 1. 数据表读取权限矩阵

| 数据资源 / 数据表 | 管理 Agent 权限 | 读取内容与用途 |
|---|---|---|
| **`agent_tasks` (任务主表)** | 🟢 **只读 (SELECT)** | 获取所有任务的状态、耗时、归属员工 ID、入参及产出概要。 |
| **`tickets` (工单流转表)** | 🟢 **只读 (SELECT)** | 审计跨岗位工单的处理时效、转接路径及最终解决结论。 |
| **`eval_logs` (考评日志表)** | 🟢 **只读 (SELECT)** | 调阅一线员工在 `agents_factory` 中的入职基线成绩，用于实战与考试表现比对。 |
| **`audit_traces` (执行轨迹表)** | 🟢 **只读 (SELECT)** | 穿透查看一线 Agent 的思考链（Thought）、Skill 真实调用入参、沙箱执行返回值。 |
| **`users` (真实用户信息表)** | 🔴 **严格脱敏读取** | 自动过滤手机号、密码、银行账号等敏感信息，仅保留 `user_id` 和抽象业务标签。 |

### 2. 写入权限与安全防护边界
* **❌ 禁止直接修改业务数据**：管理 Agent 没有 `UPDATE` 或 `DELETE` 业务表（如订单、用户、工单状态）的权限。
* **✅ 允许写入审计专用表**：管理 Agent 只能向 `supervisor_audits`（审计结论表）和 `supervisor_reports`（日报/周报表）写入分析结果。
* **✅ 允许触发标准化调度 API**：
  * `reject_task_with_feedback(task_id, reason)`：将任务驳回给一线员工重做。
  * `escalate_to_human(task_id, urgency, summary)`：将高危异常抛给人事/运维管理员。
* **🛡️ 通信隔离**：管理 Agent **物理断开与外部通信通道（如 H5、微信、飞书等）**，杜绝被黑客通过 Prompt Injection（提示词注入）实施越狱操控。

## 📡 五、 信息获取机制与底层数据管道（Data Harvesting）

管理 Agent **不需要和其他 Agent 开会聊天**，它是如何全面、实时、低成本地获取所有 Agent 的工作状态的？答案是通过三条解耦的底层数据管道：

```
                                  ┌───────────────────────────────┐
                                  │   一线员工 (Worker Agent)     │
                                  └───────────────┬───────────────┘
                                                  │
                 ┌────────────────────────────────┼────────────────────────────────┐
                 ▼ (1. 过程拦截)                  ▼ (2. 结果提交)                  ▼ (3. 实时异常)
       ┌───────────────────┐            ┌───────────────────┐            ┌───────────────────┐
       │ 审计拦截中间件    │            │ 结构化交付契约    │            │ 熔断与异常捕获    │
       │ (Skill / LLM 钩子)│            │ (Delivery JSON)   │            │ (沙箱报错/禁忌触发)│
       └─────────┬─────────┘            └─────────┬─────────┘            └─────────┬─────────┘
                 │                                │                                │
                 └────────────────────────────────┼────────────────────────────────┘
                                                  ▼
                                    ┌───────────────────────────┐
                                    │ 🗄️ 集中审计数据仓储       │
                                    │ (Postgres + 向量轨迹库)    │
                                    └─────────────┬─────────────┘
                                                  │
                                                  ▼ (按需调阅 / 定时聚合)
                                    ┌───────────────────────────┐
                                    │ 👑 内部管理督导 Agent     │
                                    └───────────────────────────┘
```

### 1. 管道一：运行时审计拦截中间件（Runtime Interceptor）
在 `server/src/aiProcessor.ts` 与 `sandboxService.ts` 中植入无感知的审计钩子（Hooks）：
* **LLM 调用截获**：每次一线 Agent 请求大模型时，自动异步记录：`prompt_tokens`、`completion_tokens`、`latency_ms`、`model`。
* **Skill 执行拦截**：每当一线 Agent 调用一个外部技能（如查询天气、写数据库、调 Python 沙箱）时，记录技能入参、执行耗时及返回值大小。

### 2. 管道二：结构化交付账单（Delivery Receipt Contract）
一线 Agent 任务结束时，必须通过系统内置的 `submit_task_receipt` 工具提交标准化账单。这个账单包含了极高密度的业务结论：
```json
{
  "task_id": "task_20260826_001",
  "agent_id": "consultant_agent_v2",
  "status": "success",
  "execution_duration_ms": 1420,
  "skills_used": ["generic_wiki_search", "refund_calculator"],
  "business_summary": "成功协助用户计算退费金额 240 元，并解答了 7 天无理由退款限制条件",
  "confidence_score": 0.96,
  "risk_flags": []
}
```

### 3. 管道三：管理 Agent 的专用工具箱（Supervisor Toolset）
管理 Agent 自身被赋予一套专门设计的**“数据穿透与审计工具”**，支持它像资深技术主管一样查数调优：

* **`query_team_work_metrics`（宏观巡检工具）**：
  * *功能*：根据时间范围、员工 ID、业务类型，拉取聚合指标（完成总数、平均耗时、报错率、驳回率）。
  * *用途*：用于第一阶段粗筛，毫秒级响应，几乎不占 Context。
* **`get_task_detailed_trace`（微观穿透工具）**：
  * *功能*：传入指定 `task_id`，调阅该任务**全生命周期所有对话原文、Thought 思考链、Skill 执行细节**。
  * *用途*：仅针对异常任务开展深度根因分析（RCA）。
* **`compare_agent_baseline_vs_live`（实战与考卷比对工具）**：
  * *功能*：比对该员工在 `agents_factory` 考评时的答题风格与当下的线上实战表现，判断是否存在提示词漂移（Prompt Drift）。

## ⚙️ 六、 核心工作流程与轻量级状态机

放弃复杂的 14 状态机，系统采用极度清晰的 **4 核心业务状态流**：

```
[ 1. 待处理 Pending ]
         │
         ▼
[ 2. 执行中 In-Progress ]  ──(遇到未授权高危操作)──> 挂起等待管理员审批
         │
         ▼
[ 3. 待质检 Awaiting_Audit ] (员工提交结构化交付账单)
         │
         ├────────────────────────────────────────┐
         ▼ (通过质检 / 抽检合格)                  ▼ (质检发现严重瑕疵/违规)
[ 4. 成功归档 Resolved ]                  [ 5. 驳回重做 Rejected ]
                                                  │
                                                  └──(附带管理Agent批注)──> 重新流转至 [2]
```

### 详细步骤说明：
1. **任务分派**：系统将任务/工单分配给合适的一线 Agent，状态进入 `In-Progress`。
2. **独立执行**：一线 Agent 调用其绑定的 Skill 在沙箱内完成任务。
3. **提交账单**：一线 Agent 输出最终答复，并向系统写入结构化元数据（包含使用的技能、耗时、关键参数），状态进入 `Awaiting_Audit`。
4. **管理督导质检（双轨制）**：
   * **常规任务**：后台自动规则过滤，直接通过归档（`Resolved`）。
   * **高风险/重点任务**：管理 Agent 进行自动审查，若发现不合规，将其标记为 `Rejected` 并附带《整改意见》，唤醒原员工进行增量修复。

## 🔍 七、 管理 Agent 的关键运行机制：两段式穿透巡检

为了防止管理 Agent 自身也发生“上下文爆炸”，管理 Agent 严格遵循 **“两段式查询机制”**：

```
【第一阶段：粗筛巡检 (轻量高效)】
管理 Agent 定时执行轻量 SQL 查询：
  "获取最近 1 小时内完成的 100 个任务概览（仅拉取 ID、状态、员工名、耗时、合规标签）"
                      │
                      ▼
            是否存在指标异常？
            ├── 否 ──> 记录正常指标，结束本轮巡检
            └── 是 ──> 触发第二阶段
                      │
                      ▼
【第二阶段：精准穿透 (深度诊断)】
管理 Agent 针对异常任务 ID 调用穿透工具：
  "get_task_detailed_trace(task_id: 'task_8848')"
拉取具体的上下文、大模型输入输出以及沙箱报错，生成《失败归因诊断书》。
```

## 🔄 八、 闭环进化：管理督导与 Agent 工厂的联动

这是本方案超越普通多 Agent 系统的最大亮点 —— **让管理层发现的问题，直接变成下一次招募和考核的试卷**：

```
                ┌──────────────────────────────────────────┐
                │ 👑 内部管理督导 Agent                    │
                │ 发现：员工 X 在解答退费政策时态度生硬     │
                └────────────────────┬─────────────────────┘
                                     │ 1. 提炼出失败 Case 与归因
                                     ▼
                ┌──────────────────────────────────────────┐
                │ 🏭 agents_factory (员工工厂)             │
                │ 自动将此 Case 加入 `eval_suites` 题库    │
                └────────────────────┬─────────────────────┘
                                     │ 2. 触发 Ralph 考评飞轮
                                     ▼
                ┌──────────────────────────────────────────┐
                │ ⚙️ ralphLoop (分数爬山与微调)             │
                │ 自动优化员工 X 的 System Prompt & 话术   │
                └────────────────────┬─────────────────────┘
                                     │ 3. 达到 95 分后生成新版本快照
                                     ▼
                ┌──────────────────────────────────────────┐
                │ 🚀 生产系统自动热更新                     │
                │ 员工 X 升级上岗，不再犯同类错误          │
                └──────────────────────────────────────────┘
```

## 🚀 九、 项目实施与落地路线图

### 第一阶段：规范交付账单与数据契约（1~2 周）
* **目标**：规范一线员工的输出，为管理层提供标准数据源。
* **任务**：
  1. 在 `agentService.ts` / `aiProcessor.ts` 中规范任务结束后的元数据写入。
  2. 保证每个任务都记录：`agent_id`、`used_skills`、`execution_time_ms`、`risk_flags`、`delivery_json`。

### 第二阶段：上线内部管理 Agent（Supervisor Agent）（2 周）
* **目标**：实现全量数据的自动化审计与异常诊断。
* **任务**：
  1. 在 `server/src/` 中新增 `supervisorService.ts`，配置专属的管理 Agent Prompt 与权限工具集。
  2. 为管理 Agent 提供 3 个核心只读工具：
     * `query_team_work_metrics`（指标粗筛）
     * `get_task_detailed_trace`（详情穿透）
     * `submit_audit_verdict`（提交质检结论与驳回指令）
  3. 配置定时任务（Cron Job，如每 30 分钟巡检一次）。

### 第三阶段：前端监控与质检工作台（1 周）
* **目标**：让平台管理员能可视化看到管理 Agent 的督导成果。
* **任务**：
  1. 在 `web/src/pages/` 中新增《团队质检大屏》或扩展 `AgentInstances.tsx`。
  2. 展示：管理 Agent 巡检记录、驳回列表、高频违规点排行、每日团队健康度打分。

### 第四阶段：全自动反哺闭环（2 周）
* **目标**：实现“发现问题 -> 自动改卷 -> 自动优化”的全自动飞轮。
* **任务**：
  1. 打通 `supervisorService` 与 `agents_factory/src/evalSuiteGenerator.ts`。
  2. 当管理 Agent 驳回次数累积达到阈值时，自动调用 `ralphLoop.ts` 重新对该 Agent 进行爬山迭代。

## 📋 十、 方案收益总结

1. **极致稳定，永不死锁**：彻底剔除 P2P 相互等待，状态机极简，调度逻辑 100% 确定性。
2. **大幅降低 Token 成本**：去除聊天社交废话，一线员工保持微型上下文，管理层只读高密度账单，总体 Token 节省 60%~80%。
3. **真正的工业级自成长**：管理 Agent 的质检结果直接反哺考评题库，实现员工能力的闭环进化。
4. **开箱即用，易于维护**：完全复用现有的 Node.js/Postgres/React 架构，无需引入复杂的分布式消息协商中间件。
