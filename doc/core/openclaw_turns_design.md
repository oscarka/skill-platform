# OpenClaw 轮次设计深度研究

> 基于 OpenClaw 最新源码调查（2026-07），整理其 AI ReAct 循环中处理"轮次限制"的完整方案。
> 无代码，全程用类比和示例说明。

---

## 一、为什么"轮次"是个大问题？

一个 AI 在执行任务时，就像一个调查员在图书馆查资料：
- 每次查一本书（工具调用）= 消耗一轮
- 找到想要的内容后，写出调查报告（最终输出）= 结束

**问题**：调查员可能一直在查书，忘记写报告。或者查到第100本书的时候，图书馆要关门了（context window 满了），这时候什么都没写出来 = 浪费。

**更深层问题**：token（对话内容）就像图书馆的容量。每查一本书（工具调用+结果），就会占用更多空间。图书馆满了，就什么都做不了了。

OpenClaw 对这个问题用了**三层防御**，而不是简单的"倒计时"。

---

## 二、OpenClaw 的三大机制

| 机制 | 类比 | 触发方式 | 作用 |
|------|------|----------|------|
| **Context Budget（上下文预算）** | 图书馆的空间监控系统 | 每次发 API 请求前自动计算 | 提前压缩历史，防止满仓 |
| **Goal Tool（目标工具）** | 调查员的工作单 | AI 主动调用 | AI 自己宣布完成或卡住 |
| **MAX_RUN_LOOP_ITERATIONS（硬顶）** | 图书馆的强制关门时间 | 外部循环计数器 | 最终兜底，防死循环 |

这三者**叠加使用**，不是选一个。

## 三、机制一：Context Budget（上下文预算）

### 核心思路

OpenClaw **不关心"第几轮"**，它关心的是"**还剩多少空间**"。

每次向 AI 发出请求之前，系统会先估算：当前对话历史消耗了多少 token？和模型的总 token 上限比，还剩多少？

### 具体数字（来自源码）

- **MIN_PROMPT_BUDGET_RATIO = 0.5**：已用 token 超过总容量的 50%，就开始考虑压缩
- **MIN_PROMPT_BUDGET_TOKENS = 8,000**：无论如何，至少保留 8000 tokens 给下一轮输入

> 📐 **举例**：模型总容量 200,000 tokens，已用 120,000（60%），超过了 50% 的阈值 → 触发压缩

### 压缩路由（四种选择）

系统检测到空间紧张后，会根据情况选择不同的压缩策略：

| 路由 | 触发条件 | 做什么 |
|------|----------|--------|
| `fits` | 空间充足 | 不压缩，正常继续 |
| `truncate_tool_results_only` | 工具结果太长，但量不多 | 截短工具调用的结果文本 |
| `compact_only` | 历史太长 | 把历史对话"摘要化"，生成更短的等价内容 |
| `compact_then_truncate` | 又长又多 | 先摘要，再截短工具结果 |

### 关键点：这和"轮次"无关

这个机制完全基于 **token 使用量**，不管 AI 用了几轮。如果每轮工具返回内容很短，可能跑 50 轮都不用压缩；如果每轮都返回巨大的网页内容，3 轮就触发压缩。

> 🔑 **对比我们的实现**：我们是"第 10 轮注入提示"——OpenClaw 是"空间不够就压缩"。本质上是两种不同的控制维度：我们控制**时间轴**（第几步），OpenClaw 控制**空间轴**（还剩多少）。

## 四、机制二：Goal Tool（目标工具）

### 核心思路

这是 OpenClaw 最精妙的设计，和"轮次限制"完全不同的思路：

**不是外部强制 AI 停止，而是给 AI 一个"工作单"，让 AI 自己宣布任务完成。**

### Goal 的三个工具

AI 在对话中永远可以使用这三个内置工具：

#### 1. `get_goal` — 查看当前工作单

AI 随时可以查看自己的任务状态和 token 消耗情况。

**返回内容示例：**
```
{
  "status": "active",
  "objective": "调研 2024 年全球新能源汽车销量前三品牌",
  "tokensUsed": 45000,
  "tokenBudget": 80000,
  "note": "任务进行中"
}
```

#### 2. `create_goal` — 创建工作单（可选）

用户或系统可以在发起任务时创建一个 goal，设定：
- **objective**：目标是什么
- **token_budget**：这个任务最多允许消耗多少 tokens

**示例：** 用户发出请求后，系统自动创建：
```
objective = "研究欧盟 AI 监管政策"
token_budget = 60000    ← 大约等于 30-40 轮工具调用的预算
```

#### 3. `update_goal` — 宣布结束

AI **主动调用**来结束任务，只有两种状态：

| 状态 | 含义 | 什么时候用 |
|------|------|-----------|
| `complete` | 任务达成 | 已经获取足够信息，输出了结果 |
| `blocked` | 真的卡住了 | **同一个障碍连续 3 轮以上**无法绕过（不是普通困难） |

> ⚠️ **注意**：`blocked` 不是"我觉得难"就可以用，OpenClaw 明确规定必须是同一个障碍连续 3 轮以上才行。普通的信息缺失、网页抓取失败，都不算理由。

### Token Budget 的作用

`get_goal` 会实时告诉 AI：**你已经用了多少 tokens，还剩多少**。

这相当于给调查员一个计时器，显示"你已经花了 45 分钟，预算是 60 分钟，快收尾了"。

AI 自己看到这个数字后，会自然地开始总结，而不需要外部注入提示。

**示例对话流：**
```
第1轮：AI 搜索欧盟 AI 法案 → fetch 网页
第2轮：AI 调用 get_goal → 发现已用 20000/60000 tokens → 继续
第3轮：AI 搜索美国监管 → fetch 网页  
第4轮：AI 调用 get_goal → 发现已用 50000/60000 tokens → 快到了
第5轮：AI 判断信息够了 → 调用 update_goal(complete) → 输出最终摘要
```

### 关键洞察

这个设计让 AI 成为**自我管理的主体**，而不是被外部强制停止的对象。AI 的结束是一个**主动决策**，不是"被掐断"。

> 🔑 **对比我们的实现**：我们用"倒数 2 轮注入"——AI 被动等提醒。OpenClaw 的 AI 主动查看自己的消耗，自己决定什么时候收手。

## 五、机制三：MAX_RUN_LOOP_ITERATIONS（硬顶）

### 核心思路

这是最后一道防线，不依赖 AI 的任何行为，纯粹是外部的**计数器保险**。

### 什么是 run loop iterations？

注意：这不是"AI 调用了几次工具"。在 OpenClaw 的架构里，一次 `run loop iteration` 指的是**一次完整的 API 尝试**，包含：
- 正常推进一轮
- 因为 rate limit 重试
- 因为模型超时重试
- 因为 context 溢出触发压缩后重启

所以 MAX_RUN_LOOP_ITERATIONS 是"**同一个用户请求，最多重试多少次**"，通常配置在 10-50 之间（根据有多少备用 provider）。

### 触发后做什么？

当重试次数耗尽，系统会根据情况选择：
1. **切换到备用模型**（如果配置了 fallback）
2. **直接返回错误**："Request failed after repeated internal retries. Please try again."

> 🔑 **这不等于"12 轮限制"**。这个计数器记的是系统层面的重试次数，和 AI 的工具调用轮次是完全不同的概念。

## 六、三层防御全景图

```
用户请求进来
     ↓
┌─────────────────────────────────────────────┐
│  每轮 AI 请求之前                            │
│                                              │
│  [Context Budget 检测]                       │
│  估算当前 token 使用量                        │
│  已用 > 50%？                                │
│  ├─ 否 → 正常发送给 AI                       │
│  └─ 是 → 先压缩历史，再发送给 AI             │
│                                              │
└─────────────────────────────────────────────┘
     ↓
┌─────────────────────────────────────────────┐
│  AI 执行过程中（每轮）                        │
│                                              │
│  AI 可以调用的工具：                          │
│  • fetch_readable（抓网页）                   │
│  • get_goal（查看已用多少 token）             │
│  • update_goal(complete)（主动结束）         │
│  • update_goal(blocked)（主动宣布卡住）      │
│                                              │
│  AI 自己决定：还要继续抓，还是总结输出？      │
└─────────────────────────────────────────────┘
     ↓
┌─────────────────────────────────────────────┐
│  外层循环保险                                 │
│                                              │
│  运行次数 >= MAX_RUN_LOOP_ITERATIONS？        │
│  ├─ 否 → 继续                                │
│  └─ 是 → 切换模型 / 返回错误信息            │
└─────────────────────────────────────────────┘
```

## 七、对比：我们的实现 vs OpenClaw

### 现状对比表

| 维度 | 我们的系统（现在） | OpenClaw |
|------|-------------------|---------|
| **轮次控制** | `max_turns=12`，外部硬顶 | `MAX_RUN_LOOP_ITERATIONS`（系统重试次数，不是工具调用次数） |
| **快超限时** | 第 10 轮注入 user 消息"快总结了" | Context Budget 检测到 token > 50%，触发压缩，不打断 AI |
| **任务结束方式** | AI 不调用工具 = 被动结束 | AI 主动调用 `update_goal(complete)` = 主动结束 |
| **卡住处理** | 跑完 12 轮失败 | AI 调用 `update_goal(blocked)` 主动上报卡住原因 |
| **历史对话处理** | 截断（简单）| 压缩摘要（保留语义） |

### 我们的方案有什么问题？

1. **"第 10 轮注入"** 不够优雅：AI 收到一条 user 消息，但这条消息根本不是用户说的，容易让 AI 产生困惑。
2. **被动结束** 没有质量信号：AI 不调用工具了，但我们不知道它是"写完了"还是"放弃了"。
3. **没有 blocked 概念**：如果某个 Skill 就是跑不通（比如需要登录才能访问的页面），AI 会一直重试直到超限，没有办法提前上报"卡住了，需要人工干预"。

### 对我们系统的三个可行改进

> 以下是方向建议，**不是要马上全改**，而是让你知道方向在哪里。

---

#### 改进 A（最小成本）：把注入位置改成 system prompt 动态注入

**现在做法：** 第 10 轮时往 messages 里插一条"假的 user 消息"

**更好做法：** 每轮都在 system prompt 里动态加一行：
```
当前已使用 8/12 轮。请合理分配剩余轮次，
当信息足够时优先输出结论而非继续抓取。
```

**优点：** AI 每轮都知道进度，不会收到奇怪的"假用户消息"，自然地调整行为。

---

#### 改进 B（中等成本）：加一个 `done` 工具

给 Executor AI 新增一个工具：

```
工具名：submit_result
参数：{"content": "最终结论文字"}
作用：AI 主动提交结果，循环结束
```

**触发逻辑：** AI 任何时候觉得信息够了，调用 `submit_result` → Executor 立即返回 `ok=True`，把 content 作为输出。

**优点：**
- AI 的结束是一个**有意义的动作**，不再是"不调用工具"这个模糊信号
- 可以在 content 里包含质量说明（如"找到了 3 个数据源，但有一个访问受限"）
- 和 OpenClaw 的 `update_goal(complete)` 完全一致的设计思路

---

#### 改进 C（系统性）：基于 token 压力而非轮次

把"第几轮"的控制改成"token 还剩多少"的控制：

```
每轮发送前计算：
  token_used / context_window_size
  如果 > 70%，在 system prompt 注入：
    "⚠️ 上下文即将用尽，请本轮给出最终结论"
```

**优点：** 对长网页和短网页都公平。抓了 3 个很长的页面 = 和抓了 12 个短页面一样，都会触发"快收尾"的提示。

---

## 八、总结：OpenClaw 设计哲学

OpenClaw 对"结束"的理解是：

> **让 AI 知道自己在哪里（已用多少资源），让 AI 自己决定什么时候收手，系统只做最后的安全网。**

不是"我倒计时给你，你停下来"，而是"我给你一个表盘，你自己看着办，实在不行我兜底"。

这个设计更尊重 AI 的推理能力，也让任务的完成更有质量——因为 AI 是在"觉得够了"时结束，而不是在"被强迫"时结束。
